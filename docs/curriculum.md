# 정보보안 종합 커리큘럼

“Alice가 로그인하면 자기 메모를 읽을 수 있다.” 이 기능을 만들려면 누가 Alice인지 확인하고, 메모의 소유자를 검사하고, 내용을 안전하게 돌려줘야 한다. 서비스를 운영하면 질문이 늘어난다. 누가 배포 권한을 갖는가? 이상 징후를 어떤 로그에서 발견하는가? 데이터를 복구한 뒤에도 각자의 메모만 보이는가? 이 과정에서는 같은 서비스를 설계하고 검토하고 복구하면서 이 질문에 답한다.

**보안 입문자 기준 40개 Chapter, Chapter당 6~8시간, 총 240~320시간**이다. Chapter마다 개념 1~2시간, 실습 3~4시간, 결과 정리와 재검증 2시간을 잡는다. 프로그래밍이 처음이라면 Chapter 3과 Chapter 16에서 변수·함수·조건문을 직접 쓸 수 있을 때까지 시간을 더 쓴다.

## 첫 실습

Linux 또는 WSL2에서 Python 3.10 이상과 Git을 준비한다. 명령은 `README.md`와 `app.py`가 있는 저장소 루트에서 실행한다. 첫 실습에는 Python 표준 라이브러리만 쓴다. 터미널이 낯설다면 `pwd`로 현재 위치를, `ls`로 파일 목록을 먼저 확인한다. [기본 명령과 도움말](bandit.md#5-기본-명령과-도움말)

```bash
python3 -m examples.network_security policy
```

출력에서 다음 세 줄을 찾는다.

```text
POLICY (model): client -> web HTTPS -> ALLOW
POLICY (model): web -> database -> ALLOW
POLICY (model): client -> database -> DENY
```

브라우저가 웹 서버에 요청하고 웹 서버가 데이터베이스를 조회하면 서비스가 동작한다. 따라서 데이터베이스는 웹 서버에서 오는 연결만 허용할 수 있다. **확인 문제** — 두 번째와 세 번째 줄은 목적지와 포트가 같다. 어떤 조건이 달라져 결과가 바뀌었는가? 코드의 `ALLOW_RULES`에서 해당 조건을 찾아 한 문장으로 적는다. 여기서 관찰한 것은 파이썬으로 작성한 네트워크 정책 모델의 판단이다. [정책 모델](../examples/network_security/policy.py)

### 백업에서 메모와 소유권 복구하기

아래 예제는 메모를 백업한 뒤 원본 DB 연결을 닫는다. 이어서 백업 사본을 새 DB에 복원한다. 두 번 호출하는 `backup`에서 왼쪽 연결이 데이터를 제공하고 괄호 안의 연결이 데이터를 받는다. 파일은 실습용 임시 폴더에 만든다. [Python의 SQLite 백업 문서](https://docs.python.org/ko/3/library/sqlite3.html#sqlite3.Connection.backup)

```bash
python3 - <<'PY'
import sqlite3
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory

notes = [(1, 1, "회의 메모"), (2, 2, "견적 메모")]
with TemporaryDirectory() as directory:
    folder = Path(directory)
    with closing(sqlite3.connect(folder / "backup.db")) as backup:
        with closing(sqlite3.connect(":memory:")) as original:
            original.execute("CREATE TABLE notes (id INTEGER PRIMARY KEY, owner_id INTEGER, body TEXT)")
            original.executemany("INSERT INTO notes VALUES (?, ?, ?)", notes)
            original.commit()
            original.backup(backup)
        with closing(sqlite3.connect(folder / "restored.db")) as restored:
            backup.backup(restored)
            rows = restored.execute("SELECT id, owner_id, body FROM notes ORDER BY id").fetchall()
    assert rows == notes
    print(rows)
PY
```

기대 출력은 `[(1, 1, '회의 메모'), (2, 2, '견적 메모')]`다. **확인 문제** — 행 개수만 세었다면 두 메모의 소유자가 서로 바뀌어도 알아낼 수 있었을까? Chapter 39에는 같은 검사를 로그인한 사용자가 보는 목록까지 확장한다.

**복구 판정 연습.** 마지막 복구 가능 시점이 09시 55분, 서비스 중단이 10시, 읽기 기능 재개가 10시 18분이었다고 하자. 되돌아간 데이터 구간은 5분이고 중단 시간은 18분이다. 이 값은 Chapter 30의 예시 목표를 모두 만족한다. 실제로 잃은 메모 건수는 해당 5분 동안의 변경 기록과 복구된 데이터를 대조해 구한다.

### 수료 기준

아래 다섯 항목을 각각 0~2점으로 채점한다. **0점**은 증거가 비어 있는 경우, **1점**은 결과와 근거가 있는 경우, **2점**은 제3자가 같은 자료로 결과를 다시 확인할 수 있는 경우다. 8점 이상을 목표로 하며, 권한 검증과 복구 검증은 각각 2점을 받아야 수료한다.

| 평가 항목 | 확인할 증거 |
|---|---|
| 설계와 위험 | 자산·신뢰 경계·보호할 속성·우선순위가 연결된 그림과 위험표 |
| 구현과 권한 검증 | 두 소유자·비로그인·빈 목록에 대한 테스트, 기존 기능의 통과 기록 |
| 배포와 데이터 보호 | 코드 버전·의존성·빌드 결과의 연결, 비밀값을 가린 로그 |
| 사고 대응과 복구 검증 | 판단 타임라인, 백업에서 복원한 행과 소유권, 목표와 실제 복구 시간 |
| 전달과 후속 조치 | 재실행 순서, 업무 영향 요약, 남은 위험의 담당자와 기한 |

마지막으로 결과물을 거버넌스(Govern)·식별(Identify)·보호(Protect)·탐지(Detect)·대응(Respond)·복구(Recover)에 대응시킨다. 예를 들어 같은 권한 회수 건에서도 책임자 지정은 거버넌스, 계정 비활성화는 보호, 이후 접근 기록 검토는 탐지의 근거가 된다. [NIST 사이버보안 프레임워크 2.0](https://www.nist.gov/cyberframework/faqs)
