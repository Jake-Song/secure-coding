# ch 12 종합 프로젝트와 재검증

[이전 ch 11](ch-11.md) · [네트워크 보안 커리큘럼](curriculum.md)

[ch 11의 통합 예제](ch-11.md)를 바탕으로 메모 조회 서비스의 오류 처리와 회귀 테스트를 완성하세요. 검사를 한 단계씩 붙이고, 어떤 단계에서 거부가 결정됐는지를 테스트 결과로 확인합니다.

## 정상 동작과 거부를 함께 검증하기

| 검증 조건 | 기대 결과 | 적합한 확인 방법 |
|---|---|---|
| 신뢰 CA·올바른 이름·유효한 요청·본인 메모 | 성공하고 본인 메모만 반환 | 실제 로컬 TLS 통합 테스트 |
| 미신뢰 CA 또는 이름 불일치 | TLS 핸드셰이크에서 인증서 오류 | 로컬 TLS 테스트, 앱 핸들러 실행 여부 확인 |
| 잘린 프레임 또는 크기 초과 | 프레임 단계에서 처리 종료 | 메모리 단위 테스트와 로컬 소켓 오류 처리 확인 |
| 필드 타입 오류 또는 MAC 불일치 | `schema` 또는 `authentication` | 검증기 단위 테스트 |
| 이미 사용한 nonce 또는 만료된 요청 | `replay` 또는 `expired` | 보호된 검증기의 고정 시계 테스트 |
| 인증은 성공했지만 다른 사용자 소유 | `forbidden`, 메모 본문 없이 거부 | 검증기 단위 테스트와 로컬 통합 테스트 |
| 한 연결에서 오류를 처리한 뒤 새 정상 연결 | 다음 정상 요청 성공 | 연속 실행 통합 테스트 |

기존 모듈의 관련 회귀 테스트를 다시 실행한 뒤 자신의 통합 테스트를 추가합니다.

```bash
python3 -m unittest -v \
  tests.test_network_protocols.FramingUnitTests \
  tests.test_network_tls.TLSSocketTests \
  tests.test_network_auth.AuthUnitTests.test_replay_fails_but_fresh_nonce_succeeds \
  tests.test_network_auth.AuthUnitTests.test_signed_request_still_needs_authorization
```

프레임 오류 후 연결을 닫더라도 다음 연결을 계속 처리할 수 있는지 확인하세요. 테스트마다 새 nonce와 예상 시각을 정하고, 재전송 거부를 확인하는 테스트에서는 하나의 검증 상태를 공유합니다. 테스트 기록에는 TLS 오류처럼 응답 프레임이 생성되기 전의 실패와, 연결 안에서 오류 응답을 받은 경우를 구분해 적습니다.

## 보고서와 평가

실행 환경·기준 커밋·재실행 명령을 기록합니다. 이어서 프레임 형식, 요청 스키마, 신뢰 경계, 예상과 실제 결과, 수정 근거를 적습니다. 임시 키와 인증서가 언제 만들어지고 폐기되는지, 고정 시계와 메모리 저장소로 검증한 범위도 포함합니다.

| 평가 항목 | 비중 | 확인할 증거 |
|---|---:|---|
| 코드 이해와 명세 | 25% | 처리 순서와 단계별 책임을 설명한 그림·코드 |
| 정상 동작 | 25% | 신뢰할 수 있는 연결에서 정상 메모를 반환한 결과 |
| 거부와 회귀 검증 | 35% | 실패 지점별 거부 결과와 이후 정상 동작 확인 |
| 재현성과 기록 | 15% | 실행 명령, 환경, 검증 범위, 민감정보를 가린 로그 |

**확인 문제.** 타인의 메모 요청이 거부됐다는 결과만으로 MAC 검사와 소유권 검사 중 어느 쪽이 거부했는지 알 수 있나요? 그 지점을 확인하려면 어떤 조건을 기록해야 하나요?

**제출물.** 통합 서비스 소스, 실행 명령, 회귀 테스트, 보고서를 제출하세요. 보고서에서 각 경계의 실패 이유와 정상 기능 유지 여부를 바로 찾을 수 있게 결과를 연결하세요.
