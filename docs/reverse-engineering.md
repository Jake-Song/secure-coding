# 역엔지니어링 12주 커리큘럼

**입문자 기준 주 6~8시간, Linux x86-64 실행 파일 분석 과정**입니다. C 프로그램부터 시작해 소스 없이 함수의 역할과 입력 형식을 추론하고, 디버거와 재구현으로 검증하는 것을 목표로 합니다.

역엔지니어링은 프로그램의 구조와 동작을 알아내는 전체 분석 활동입니다. 디스어셈블은 기계어를 어셈블리로, 디컴파일은 실행 코드를 고수준 의사 코드로 표현하는 기법입니다. 반드시 둘을 순서대로 거쳐야 하는 것은 아닙니다. 디컴파일 결과가 원래 변수명·자료형·소스를 복원해 주는 것도 아닙니다.

## 시작 수준과 환경

- 터미널의 파일 탐색·권한·프로세스가 낯설면 [Bandit 시작하기](bandit.md)와 [Linux 기초 실습](foundations.md#1주차-linux)을 먼저 진행합니다. 준비 기간은 본과정과 별도로 1~2주를 잡습니다.
- 변수·조건문·반복문·함수를 작성할 수 있다고 가정합니다. 프로그래밍이 처음이면 [C 언어 입문 튜토리얼](c-tutorial.md)로 같은 개념을 익히는 준비 기간을 2~4주 추가합니다.
- C의 포인터·구조체·메모리는 1~2주차에 다룹니다. 웹 보안 과정을 먼저 마칠 필요는 없습니다.
- 실습 대상은 직접 만든 프로그램과 분석이 허용된 교육용 바이너리입니다.

기준 환경은 **x86-64 Linux 또는 x86-64 Windows의 WSL2 Linux**입니다. Apple Silicon·ARM Linux에서는 x86-64 Linux 가상 머신이나 교육 플랫폼을 사용합니다. ARM용으로 컴파일한 결과에 이 문서의 레지스터·호출 규약을 그대로 적용하지 않습니다.

| 도구 | 용도 | 도입 시점 |
|---|---|---|
| GCC, `file`, GNU Binutils의 `readelf`·`objdump`·`strings`·`strip` | 빌드, 파일 분류, ELF·명령어·심볼 확인 | 1주차부터 |
| GDB | 실행 중 중단, 레지스터·메모리·호출 흐름 관찰 | 2주차부터, 6주차 집중 |
| Ghidra | 함수·참조·제어 흐름·디컴파일 분석 | 5주차부터 |
| Python 3 | 입력 생성, 바이트 처리, 분석 결과 재구현 | 8주차부터 |

Ubuntu/Debian 계열의 실습 머신에서 기본 도구를 준비하는 예입니다.

```bash
sudo apt update
sudo apt install build-essential binutils file gdb python3
uname -m
gcc --version
gdb --version
```

`uname -m`의 기대값은 `x86_64`입니다. Ghidra는 [공식 설치 안내](https://github.com/NationalSecurityAgency/ghidra#install)에 따라 설치하고, 선택한 릴리스의 JDK 요구사항을 확인합니다. OS·아키텍처·컴파일러·분석 도구의 버전을 기록합니다.

## 매주 학습 방식

개념 1~2시간, 실습 3~4시간, 기록과 재검증 2시간을 배분합니다.

1. 입력·출력·종료 코드 등 확인하려는 질문을 정합니다.
2. 파일 정보와 정적 분석으로 가설을 세웁니다.
3. 필요할 때 실행·중단점·메모리 관찰로 가설을 검증합니다.
4. 추론한 동작을 의사 코드나 작은 프로그램으로 표현합니다.
5. 정상·오류·경계 입력을 비교하고, 확인한 사실과 남은 추측을 기록합니다.

처음에는 소스와 바이너리를 함께 봅니다. 이후 소스를 읽기 전에 분석 보고서를 작성하고 마지막에 대조합니다. 독립 분석 평가는 다른 사람이 만든 작은 교육용 프로그램으로 진행합니다.

## 1~4주차 기반 만들기

실행 가능한 예제와 단계별 설명은 [1~4주차 학습자료](reverse-engineering-labs.md)에 있습니다. [1주차 C와 빌드](reverse-engineering/week-01.md), [2주차 메모리](reverse-engineering/week-02.md), [3주차 명령어](reverse-engineering/week-03.md), [4주차 호출과 ELF](reverse-engineering/week-04.md) 순서로 진행합니다.

### 1주차 C와 컴파일

아래의 [첫 실습](#첫-실습)을 실행한 뒤 `if`, `for`, `switch`, 함수 호출이 각각 들어간 짧은 프로그램을 만듭니다. `gcc -E`로 전처리 결과, `gcc -S`로 어셈블리, `gcc -c`로 오브젝트를 만듭니다.

`int`와 `unsigned int`, 문자 배열과 널 종료 문자열을 비교합니다. `sizeof`는 저장 크기, `strlen`은 널 종료 전 문자열 길이라는 차이를 확인합니다.

완료 기준: 함수의 입력·출력·종료 코드와 빌드 단계를 설명하고, 실행 파일에는 명령어 외에 데이터와 메타데이터도 있음을 확인합니다.

### 2주차 메모리와 자료형

지역 변수, 전역 변수, 문자열 리터럴, 동적 할당 객체를 만듭니다. GDB에서 주소를 조사하고 작은 구조체의 필드 오프셋과 패딩을 비교합니다. 유효한 범위만 읽고, 해제한 포인터를 역참조하지 않습니다.

`0x12345678`을 저장한 정수의 바이트 순서를 관찰합니다. 값, 그 값의 주소, 주소에 저장된 바이트를 구분해 적습니다. 지역 변수가 항상 스택에 남거나 `malloc`이 항상 같은 메모리 매핑에서 할당된다고 가정하지 않습니다.

완료 기준: `p`, `*p`, `&p`를 구분하고 함수 종료와 `free` 이후 객체 수명을 설명합니다.

### 3주차 명령어와 제어 흐름

Intel 문법으로 `mov`, `lea`, `add/sub`, `and/or/xor`, `shl/shr`, `cmp/test`, 조건 분기, `call/ret`를 익힙니다. 암기보다 C 예제의 동작과 연결하는 데 집중합니다.

- `rax/eax/al`의 관계와 32비트 레지스터 쓰기가 상위 비트에 미치는 영향을 관찰합니다.
- `lea`의 주소 계산과 메모리 읽기를 구분합니다.
- 비교 후 어떤 플래그를 어떤 분기가 사용하는지 추적합니다. signed/unsigned 비교를 구분합니다.
- 루프의 초기값·종료 조건·갱신 지점을 찾아 제어 흐름 그림을 그립니다.

완료 기준: 짧은 함수 3개의 결과를 예측하고 실행 결과와 대조합니다.

### 4주차 함수 호출과 실행 파일

Linux의 System V AMD64 ABI를 기준으로 단순한 정수·포인터 인자의 `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` 전달과 `rax` 반환을 추적합니다. 부동소수점·구조체 인자 및 시스템 콜은 규칙이 다를 수 있으므로 별도로 다룹니다. Windows x64 호출 규약과 혼용하지 않습니다. 세부 규칙은 [x86-64 psABI](https://gitlab.com/x86-psABIs/x86-64-ABI)를 참고합니다.

`readelf -h`, `-S`, `-l`, `-s`로 헤더·섹션·세그먼트·심볼을 조사합니다. `.text`, `.rodata`, `.data`, `.bss`의 역할과 파일에 실제 바이트가 있는지를 비교합니다. 섹션은 링크·분석 관점, 세그먼트는 로더의 메모리 매핑 관점에서 봅니다. 옵션은 [GNU readelf 문서](https://sourceware.org/binutils/docs/binutils/readelf.html)를 참고합니다.

완료 기준: ELF 진입점과 C의 `main`을 구분하고, PIE·ASLR 때문에 정적 주소와 실행 중 주소가 달라질 수 있음을 설명합니다.

## 5~8주차 분석과 재구현

### 5주차 Ghidra

첫 실습 바이너리를 가져와 아키텍처·비트 수를 확인하고 자동 분석합니다. `accepted` 문자열의 참조에서 시작해 입력 처리→검사→출력 경로를 연결합니다. 역할을 파악한 함수·변수에 이름을 붙이고 자료형을 수정합니다. 핵심 조건을 Listing의 실제 명령어와 대조합니다.

완료 기준: 함수 역할의 근거를 참조·분기·데이터 접근으로 설명합니다. 디컴파일러의 임시 변수명이나 추정 자료형을 사실로 단정하지 않습니다.

### 6주차 GDB

첫 실습의 명령으로 시작해 `break`, `run`, `continue`, `stepi`, `nexti`, `finish`, `info registers`, `x`, `disassemble`, `bt`를 익힙니다. `stepi`는 호출 함수 안으로 들어가며, `nexti`는 호출을 넘겨 관찰하는 데 사용합니다. 명령별 동작은 [GDB 공식 설명서](https://sourceware.org/gdb/current/onlinedocs/gdb.html/)를 참고합니다.

완료 기준: 입력 위치와 비교 조건, 결과를 결정하는 분기를 두 입력의 실행 경로로 보여 줍니다. 주소는 실행마다 확인하며 다른 환경의 고정 주소를 복사하지 않습니다.

### 7주차 입력 검증

고정 문자열 비교에서 출발해 길이 검사→문자 범위 검사→바이트별 변환→누적값 비교가 있는 교육용 프로그램을 분석합니다. 수락되는 입력 하나를 찾은 뒤 길이 부족·길이 초과·한 바이트 변경 입력의 실패 조건을 조사합니다.

완료 기준: 수락 조건을 의사 코드로 적고 조건을 만족하는 입력을 생성합니다. 수락 조건을 설명하는 것과 실행 중 값을 바꿔 결과를 바꾸는 것을 구분합니다.

### 8주차 알고리즘 재구현

바이트마다 XOR와 덧셈을 적용하거나 32비트 누적값을 계산하는 예제를 분석합니다. Python의 정수는 C의 고정 폭 unsigned 정수와 다르게 동작하므로 필요에 따라 `& 0xff`, `& 0xffffffff`로 절단합니다.

완료 기준: 원본과 재구현에 같은 입력 10개 이상을 넣고 결과를 비교합니다. 빈 입력, 최소·최대 길이, 경계 바이트를 포함합니다. 명령행 인자로 전달할 수 없는 NUL 바이트는 파일·표준 입력을 받는 예제에서 다룹니다. 간단한 XOR 변환을 현대 암호 분석으로 확대 해석하지 않습니다.

## 9~12주차 독립 분석

### 9주차 파일 형식

magic 4바이트, 버전 1바이트, little-endian 길이 2바이트, 가변 payload로 구성한 교육용 파일 파서를 준비합니다. 분석 단계에서는 명세를 가리고 파서가 읽는 오프셋과 비교 조건으로 형식을 추론합니다. 혼자 공부하면 [pwn.college의 파일 형식 역공학 실습](https://pwn.college/intro-to-cybersecurity/reverse-engineering/)에서 작은 과제를 선택해 독립 분석을 연습할 수 있습니다.

완료 기준: 오프셋·크기·엔디언·필드 의미를 명세로 만들고 생성기로 정상 파일을 만듭니다. 잘린 헤더·길이 불일치·지원하지 않는 버전의 동작도 기록합니다. 비정상 종료가 발생하면 관찰한 현상과 추정 원인을 구분합니다.

### 10주차 최적화와 심볼

같은 소스에서 `-O0 -g`, `-O2 -g`, `-O2` 빌드와 마지막 빌드의 strip 복사본을 비교합니다. 최적화 변화와 심볼 제거 효과를 각각 관찰합니다. 인라이닝·상수 전파·루프 변형·프레임 포인터 생략은 관찰 대상이며 모든 예제에서 발생해야 하는 결과가 아닙니다. 설정은 [GCC 최적화 문서](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)를 참고합니다.

완료 기준: 함수명·디버그 정보가 없어져도 남는 문자열·외부 함수 참조·동작으로 핵심 로직을 찾습니다. strip이 디컴파일 방지나 암호화를 의미하지 않음을 설명합니다.

### 11주차 패치

자기 프로그램의 복사본에서 `accepted`를 같은 바이트 길이의 `observed`로 바꾸고 널 종료 바이트를 보존합니다. 원본은 남겨 둡니다. 추가 과제는 작은 분기 하나를 수정하고 입력별 동작 변화를 설명하는 것입니다.

- 파일 오프셋과 가상 주소를 구분합니다. 파일에 저장된 `PT_LOAD` 범위에서는 `파일 오프셋 = p_offset + (정적 가상 주소 - p_vaddr)`로 대응시킵니다. PIE 실행 주소라면 먼저 로드 바이어스를 제거합니다. `.bss`처럼 파일에 없는 영역에는 그대로 적용하지 않습니다.
- 변경 위치·원래 바이트·새 바이트·변경 이유와 전후 해시를 기록합니다.
- 디버거에서 메모리를 바꾸는 것은 실행 파일을 저장하는 패치와 다릅니다.
- 분기 패치는 명령어 길이·상대 주소·다른 분기의 도착 지점을 확인합니다. 주소와 opcode는 자기 빌드에서 결정합니다.

완료 기준: 파일 차이와 동작 차이가 대응하고, 복사본을 새로 실행해도 변경이 유지됩니다. 동작 변경과 원래 입력 규칙의 복원을 별도 성과로 기록합니다.

### 12주차 최종 프로젝트

핵심 함수 3~5개, 입력 형식 하나, 분석할 알고리즘 하나를 가진 교육용 ELF로 제한합니다. 다른 학습자나 출제자가 만든 바이너리 또는 공식 교육 과제에서 고릅니다. 프로젝트 기간에는 원본 소스를 보지 않습니다.

제출물:

1. 대상 출처·허용 범위·SHA-256·환경·분석 질문.
2. 함수 관계도, 입력에서 출력까지의 흐름, 핵심 분기의 근거 주소.
3. 복원한 입력 규칙 또는 파일 형식과 알고리즘 의사 코드.
4. 재구현, 입력 10개 이상의 원본/재구현 비교, 남은 불일치.
5. 재현 명령, 실행 기록, 확인된 사실·추론·미확인 사항.

| 평가 항목 | 비중 | 확인 내용 |
|---|---|---|
| 구조·동작 설명 | 30% | 함수·데이터·입출력 관계가 실제 코드와 연결되는가 |
| 분석 근거 | 30% | 정적·동적 관찰이 주장과 대응하는가 |
| 재구현과 비교 | 25% | 정상·오류·경계 입력에서 일치하는가 |
| 재현성과 기록 | 15% | 환경·명령·제약을 다른 사람이 따라갈 수 있는가 |

## 첫 실습

실습 파일과 빌드 결과를 임시 디렉터리에 만듭니다. 다음 블록을 터미널에서 실행합니다.

```bash
lab_dir=$(mktemp -d /tmp/reverse-lab.XXXXXX)
cd "$lab_dir"
cat > check.c <<'EOF'
#include <stdio.h>
#include <string.h>

static int check(const char *input) {
    return strlen(input) == 5 && strcmp(input, "trace") == 0;
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fprintf(stderr, "usage: %s INPUT\n", argv[0]);
        return 2;
    }
    int ok = check(argv[1]);
    puts(ok ? "accepted" : "rejected");
    return ok ? 0 : 1;
}
EOF
gcc -std=c11 -Wall -Wextra -O0 -g -fno-omit-frame-pointer check.c -o check-debug
gcc -std=c11 -Wall -Wextra -O2 -g check.c -o check-opt-debug
gcc -std=c11 -Wall -Wextra -O2 check.c -o check-opt
cp check-opt check-stripped
strip check-stripped
```

아래 명령으로 출력·종료 코드·파일 정보를 관찰합니다.

```bash
./check-debug trace
echo $?
./check-debug wrong
echo $?
./check-debug
echo $?
file check-debug check-stripped
readelf -h check-debug
readelf -S check-debug
readelf -l check-debug
readelf -s check-debug
strings -a check-stripped
objdump -d -M intel check-debug
objdump -d -M intel check-stripped
```

기대 결과는 `trace`→`accepted`·종료 코드0, `wrong`→`rejected`·1, 인자 없음→사용법 표시·2입니다. 나머지 세 빌드에서도 비교합니다. `trace` 이외의 5글자나 길이4·6의 입력도 시험해 길이만으로 조건이 성립하지 않음을 확인합니다.

디버그 버전을 GDB로 엽니다.

```bash
gdb -q ./check-debug
```

다음 명령은 GDB 프롬프트에서 입력합니다.

```gdb
set disassembly-flavor intel
break check
run trace
print input
x/s input
disassemble /r check
info registers
x/8i $pc
stepi
nexti
finish
continue
quit
```

`wrong`으로도 관찰합니다. 명령어와 바이트 표시 방법은 [GDB 기계어 표시 가이드](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Machine-Code.html)를 참고합니다. strip 버전에는 일반적으로 `check` 이름이 남지 않으며, 최적화로 독립된 함수 자체가 없어질 수도 있으므로 같은 이름의 중단점이 사용 가능하다고 가정하지 않습니다.

첫 제출물은 `main`→`check`→비교→출력의 그림, 성공·실패 조건, 관련 명령어와 관찰값입니다. 이 예제는 문자열을 숨기지 않았으므로 `strings`에서 찾은 값이 실제 판정에 사용된다는 점을 참조와 실행으로 확인합니다.
