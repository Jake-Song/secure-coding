# 웹 보안 커리큘럼

## 목표와 학습 방식

**주 6~8시간, 입문자 기준**입니다. 네트워크 기초인 1주차부터 시작해 웹·API를 중심으로 학습합니다. 최종 목표는 작은 서비스에서 데이터 흐름과 신뢰 경계를 추적하여 취약점을 재현하고, 원인을 설명하며, 수정과 회귀 테스트까지 수행하는 것입니다.

실습은 자신의 로컬 앱 또는 명시적으로 실습을 허용한 환경에서 진행합니다. 실제 개인정보·운영용 비밀정보 대신 예제 데이터를 사용합니다.

매주 다음 순서를 반복합니다.

1. 정상 요청과 기대 동작을 확인한다.
2. 신뢰 경계와 누락된 검사를 가정한다.
3. 요청·응답·서버 상태로 취약점을 재현한다.
4. 입력이 코드·쿼리·HTML 등으로 해석되는 위치를 찾는다.
5. 수정 후 공격 차단과 정상 기능 유지를 함께 검사한다.
6. 재현 요청, 원인 코드, 수정 이유, 테스트 결과를 기록한다.

시간 배분 예: 개념 1시간, 재현·분석 2시간, 수정·테스트 2시간, 보고서 1시간. 남는 시간에는 공식 교육 실습 1~2개를 추가합니다.

## 공통 준비

명령은 Linux·macOS 또는 WSL의 저장소 루트에서 실행합니다. 웹 실습에는 Python 3.10 이상이 필요합니다. `.venv`에 의존성을 설치한 적이 있다면 바로 `source .venv/bin/activate`부터 시작하세요. 터미널을 새로 열면 활성화 명령도 다시 실행합니다.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

`ensurepip` 오류가 나거나 `uv`로 새 가상환경을 만든다면 아래 명령을 사용하세요.

```bash
UV_CACHE_DIR=/tmp/secure-coding-uv-cache uv venv .venv
UV_CACHE_DIR=/tmp/secure-coding-uv-cache uv pip install --python .venv/bin/python -r requirements.txt
source .venv/bin/activate
```

가상환경을 활성화한 터미널에서 `python app.py`를 실행하고 브라우저나 다른 터미널에서 `http://127.0.0.1:5000/`에 접속합니다. 앱을 재시작하면 메모리의 데이터와 세션이 초기화됩니다.

| 예제 계정 | 비밀번호 | 소유한 메모 ID |
|---|---|---:|
| `alice` | `alice-lab` | 1 |
| `bob` | `bob-lab` | 2 |

## 1~3주차 기반 만들기

- **1주차:** 작은 TCP 에코 예제로 연결·송수신·half-close·EOF를 관찰합니다. HTTP의 메서드·상태 코드·헤더·본문을 구분합니다.
- **2주차:** `create_app`, 로그인, `current_user`, 메모 조회, SQL 실행 코드를 읽습니다. `/about` 같은 읽기 전용 라우트를 직접 추가하고 한글·HTML 특수문자를 출력해 봅니다. 사용자 입력을 그대로 HTML 문자열에 연결하지 않습니다.
- **3주차:** Burp로 자신의 앱 요청을 반복 전송합니다. 응답 코드만 보지 말고 어떤 계정으로 어떤 데이터가 조회·변경됐는지 확인합니다.

2주차의 쿠키는 서버 세션 식별자를 담습니다. Flask 서명 쿠키는 암호화된 비밀 저장소가 아니므로 비밀번호를 넣지 않습니다. 이 예제는 별도 메모리 목록에서 세션 유효성을 검사하고 로그아웃 시 해당 세션을 제거합니다.

## 4~7주차: 주요 웹 취약점

[전체 일정](#전체-일정)에서 4~7주차 학습자료를 열어 정상 동작과 방어 조건을 확인합니다. `/safe/`를 먼저 읽지 않고 수정 방향을 작성한 다음 구현과 비교합니다.

- **4주차 제출물:** Alice·Bob·비로그인 사용자가 메모 1·2에 접근하는 표. ID를 숨기는 것과 소유권을 검사하는 것의 차이.
- **5주차 제출물:** 입력이 SQL 문법으로 바뀌는 위치, 바인딩 후 쿼리 구조가 유지되는 이유, 정상 검색 테스트.
- **6주차 제출물:** 브라우저 제목 변경 재현, 취약/방어 HTML 비교. HTML 텍스트 인코딩을 JavaScript·URL 문맥에 그대로 적용할 수 없는 이유. 저장형·DOM XSS는 공식 교육 실습으로 확장.
- **7주차 제출물:** 다른 origin의 폼 전송 결과, 쿠키 전송 관찰, 토큰 검증 결과. CORS·SameSite·CSRF 토큰이 각각 다루는 문제 설명.

## 8~10주차: 경계와 방어 운영

- **8주차:** `python examples/boundaries.py` 실행 후 명령어의 문자열/인자 목록 차이, 공개 디렉터리 이탈, 서버 생성 업로드 이름을 설명합니다. 정상 파일, `../` 경로, 심볼릭 링크, 비 UTF-8·초과 크기 입력을 비교합니다.
- **9주차:** 가상 SSRF 목적지 변경과 `/vuln/profile`의 관리자 승격을 재현합니다. 목적지 선택 권한과 속성 수정 권한을 각각 서버에서 제한합니다. 실제 SSRF에서는 DNS 결과, 리다이렉트, IPv4/IPv6, 연결 시점, 네트워크 정책을 추가로 고려해야 함을 정리합니다.
- **10주차:** 코드의 민감한 지점과 의존성을 검토하고 거부 로그를 관찰합니다. 해시·암호화·인코딩을 구분하며, 비밀번호는 전용 비밀번호 해시 함수로 저장하고 로그에는 비밀번호·세션·CSRF 토큰을 남기지 않습니다.

## 11주차: 최종 프로젝트

예제 앱의 취약 경로 3~5개를 직접 수정합니다. 첫 재현을 보존한 뒤 수정 코드를 작성하고, 공격 차단·정상 기능·권한 경계에 대한 회귀 테스트를 추가합니다. 기존 테스트가 취약 동작을 기대하는 경우 해당 기대값을 수정 후 기준으로 바꿉니다.

이 저장소는 경로명에 취약점 여부가 드러나므로 블라인드 평가용은 아닙니다. 독립 분석을 연습하려면 교육용 앱에서 문제 설명을 보지 않고 기능과 코드부터 조사합니다.

평가 기준:

| 항목 | 비중 | 확인 내용 |
|---|---|---|
| 재현·영향 | 25% | 필요한 계정·요청·상태·결과가 재현 가능한가 |
| 원인 분석 | 25% | 신뢰 경계와 누락된 검사를 코드로 설명하는가 |
| 수정 | 25% | 원인을 해결하며 정상 기능을 유지하는가 |
| 재검증·기록 | 25% | 회귀 테스트와 로그, 검증 한계가 명확한가 |

- **클라우드·컨테이너 보안:** IAM, 네트워크 경계, 비밀정보 관리, 이미지·의존성, 최소 권한.
- **탐지·침해 분석:** 접근·애플리케이션 로그, 패킷, 타임라인, 탐지 규칙, 대응 후 검증.
