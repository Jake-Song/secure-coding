# ch 8 명령어·파일·업로드 경계

## 왜 이 경계를 배우나

웹 서버가 받은 값은 단순한 문자열로 끝나지 않고 셸, 파일시스템, 파일 형식 처리기로 넘어갈 수 있습니다. 공격자는 그 값의 **내용**뿐 아니라 값이 해석되는 **경계**를 바꿉니다. 따라서 공격은 보통 다음 팩터가 함께 있을 때 성립합니다.

1. 공격자가 값의 일부를 제어합니다.
2. 서버가 그 값을 명령어·경로·파일명처럼 다시 해석합니다.
3. 그 동작이 공격자보다 큰 서버 권한으로 수행됩니다.
4. 검사와 실제 사용 사이에 다른 해석이나 저장 단계가 남아 있습니다.

| 기능 | 주요 공격 팩터 | 공격자가 노리는 결과 | 이 장에서 끊는 경계 |
|---|---|---|---|
| 명령 실행 | 입력이 명령 문자열에 섞이고 셸이 제어 문법까지 해석함 | 원래 의도하지 않은 명령 실행 | 실행 파일과 인자를 리스트로 분리하고 셸 해석을 제거함 |
| 파일 읽기 | 사용자가 경로를 정하고 `..` 또는 심볼릭 링크로 실제 위치를 바꿈 | 공개 범위 밖 파일 읽기 | 실제 경로를 해석한 뒤 허용 디렉터리 안인지 확인함 |
| 파일 업로드 | 클라이언트가 이름·확장자·크기·내용을 정하고 서버가 그대로 저장함 | 경로 이탈, 파일 덮어쓰기, 이후 처리기의 오용 | 허용 조건을 검사하고 서버가 새 파일명을 정해 제한된 위치에 저장함 |

이 표를 기준으로 보면 이 장의 목표는 공격 문자열 몇 개를 외우는 것이 아닙니다. **어떤 입력이 어디에서 새로운 의미로 해석되고, 그때 어떤 권한이 사용되는지 추적한 뒤, 해석 이전의 구조적 경계에서 차단하는 것**입니다. 아래 예제에서 `safe=False`와 `safe=True`의 차이를 비교할 때도 이 세 가지 공격 팩터를 표시하세요.

## 경계를 넘는 공격의 공통 과정

여기서 “경계를 넘는다”는 것은 문자열이 물리적으로 다른 곳으로 이동한다는 뜻이 아닙니다. 입력이 원래의 **데이터**로 남아 있어야 하는데, 서버의 다음 단계에서 **명령어 문법·파일 경로·파일 형식**으로 다시 해석되는 것을 뜻합니다.

```text
공격자 입력
    ↓
웹 요청 필드
    ↓  (검사 없이 결합·정규화·저장)
셸 / 파일시스템 / 파일 처리기
    ↓
서버 권한으로 실행·읽기·쓰기·후속 처리
```

따라서 각 기능을 분석할 때는 다음 네 질문을 순서대로 답하세요.

1. 공격자가 조절할 수 있는 값은 정확히 어디까지인가?
2. 그 값이 다음 단계에서 어떤 문법이나 규칙으로 해석되는가?
3. 해석 결과로 서버가 가진 어떤 권한을 사용하게 되는가?
4. 검사한 값과 실제로 사용한 값이 같은가?

### 1. 명령어 경계: 데이터가 셸 문법이 되는 경우

취약한 흐름은 보통 `고정 명령어 + 사용자 문자열`을 하나의 명령 문자열로 만든 뒤 셸에 전달합니다.

```text
value = "hello; printf LAB_MARKER"
f"printf '%s' {value}"
                 ↓
셸이 공백과 ; 를 문법으로 해석
                 ↓
printf '%s' hello  ;  printf LAB_MARKER
```

` ; `는 `printf`에 전달되는 글자가 아니라 셸의 명령 분리 연산자가 됩니다. 그래서 공격자는 원래 프로그램의 인자 하나를 바꾸는 데서 그치지 않고, 뒤에 별도의 명령을 붙일 수 있습니다. 현재 예제는 실제 파일 변경이나 네트워크 요청 대신 `LAB_MARKER`를 출력하도록 만들어 이 해석 차이만 관찰하게 합니다.

리스트 방식에서는 각 요소가 별도 인자입니다.

```python
subprocess.run(["printf", "%s", value], shell=False, check=True)
```

이때 `;`는 셸 문법으로 재해석되지 않고 `printf`가 출력할 데이터로 남습니다. 이것이 “위험한 문자를 지웠다”가 아니라 **명령 구조와 데이터를 분리했다**는 방어입니다.

단, 셸을 끈 것만으로 모든 명령 실행 문제가 해결되는 것은 아닙니다. 사용자가 `-`로 시작하는 값을 옵션으로 해석하게 하거나, 실행 파일 자체를 선택하게 하면 셸이 없어도 프로그램의 동작을 바꿀 수 있습니다. 실행 파일은 고정하거나 허용 목록으로 제한하고, 각 옵션은 허용 타입·범위·문자 집합을 별도로 정의해야 합니다.

### 2. 파일 경계: 논리적 경로가 실제 위치로 바뀌는 경우

파일 읽기에서는 사용자가 보낸 `name`을 공개 디렉터리에 붙입니다.

```text
public / name
```

공격자가 `../secret.txt`를 보내면 문자열만 볼 때는 `public/../secret.txt`이지만, 운영체제가 경로를 해석한 실제 위치는 다음과 같습니다.

```text
/tmp/fixture/public/../secret.txt
                         ↓ resolve()
/tmp/fixture/secret.txt
```

즉 `..`은 파일 이름의 일부가 아니라 부모 디렉터리로 이동하는 경로 규칙입니다. `safe=False`에서는 실습 fixture 안에 있다는 조건만 확인하므로 이 이동이 허용되고, `safe=True`에서는 최종 위치가 `public` 아래인지 다시 확인하므로 거부됩니다.

심볼릭 링크는 같은 문제를 다른 형태로 만듭니다.

```text
public/link.txt  ──심볼릭 링크──>  ../secret.txt
```

입력 이름 `link.txt`만 검사하면 공개 디렉터리 안처럼 보이지만, 링크를 따라간 최종 대상은 공개 범위 밖입니다. 그래서 이 예제는 입력 문자열이 아니라 `resolve()` 후의 실제 경로를 검사합니다. 문자열에서 `../`만 삭제하는 방식은 인코딩·중복 구분자·심볼릭 링크를 제대로 다루지 못합니다.

실제 서비스에서는 검사한 뒤 파일을 열기 전 대상이 바뀌는 경쟁 조건(TOCTOU)도 고려해야 합니다. 중요한 파일에는 디렉터리 핸들 기반 API, 심볼릭 링크 추적 방지 옵션, 운영체제 권한 같은 추가 통제가 필요합니다. 이 실습의 `resolve()` 예제는 경로 순회와 링크의 개념을 보여주는 교육용 방어이지 모든 파일시스템 경쟁 조건을 해결하는 구현은 아닙니다.

### 3. 업로드 경계: 클라이언트 이름이 서버 저장 규칙에 들어가는 경우

업로드에는 파일명, 확장자, 내용, 크기라는 서로 다른 입력이 있습니다. 이 값을 모두 신뢰하면 공격자는 다음 경계를 연속해서 건드립니다.

```text
HTTP multipart 입력
    ├─ 파일명 ──> 저장 경로·충돌 대상
    ├─ 확장자 ──> 나중에 적용될 처리기
    ├─ 내용 ────> 디코더·압축 해제기·이미지 처리기
    └─ 크기 ────> 메모리·디스크·처리 시간
```

예를 들어 서버가 클라이언트 파일명을 그대로 저장하면 `../../memo.txt`가 업로드 디렉터리 밖의 경로로 해석될 수 있습니다. 같은 이름의 파일을 덮어쓸 수도 있습니다. 업로드 디렉터리가 웹에서 실행되거나 직접 제공된다면, 확장자와 내용이 이후 브라우저·스크립트·문서 처리기의 해석까지 바꿀 수 있습니다.

현재 `save_text_upload`는 **텍스트 첨부 하나만** 가정합니다.

- `.txt` 확장자만 허용합니다.
- 1 KiB를 넘으면 거부합니다.
- 실제 바이트를 UTF-8로 디코딩해 텍스트 조건을 확인합니다.
- 클라이언트 이름을 저장 경로로 사용하지 않고 서버가 랜덤한 이름을 만듭니다.
- `xb`로 새 파일만 만들도록 해 기존 파일 덮어쓰기를 피합니다.

따라서 `../../memo.txt`를 보내도 저장 위치는 `uploads` 안에 남고, 반환된 이름도 `memo.txt`가 아닙니다. 이것은 “확장자가 `.txt`면 안전하다”는 뜻이 아닙니다. 이미지·압축 파일·PDF·문서에는 각각의 파서와 폭탄 입력, 메타데이터, 콘텐츠 검증 정책이 필요하며, 이 예제의 검사를 그대로 일반화하면 안 됩니다.

### 세 공격의 차이와 공통점

| 경계 | 입력이 바뀌는 의미 | 서버가 수행하는 동작 | 구조적 방어 |
|---|---|---|---|
| 명령어 | 데이터 → 셸 문법·옵션 | 다른 명령 또는 다른 옵션 실행 | 인자 리스트, 고정 실행 파일, 옵션별 allowlist |
| 파일 경로 | 파일명 → 실제 경로·링크 대상 | 허용 범위 밖 읽기·쓰기 | 최종 경로 해석 후 범위 확인, 서버 생성 이름 |
| 업로드 | 이름·내용 → 저장 대상·후속 처리 형식 | 덮어쓰기·파서 오용·자원 고갈 | 크기·형식 검사, 격리 저장, 충돌 방지 이름 |

공통된 원인은 “입력값을 검사하지 않았다”보다 더 구체적입니다. **서버가 입력을 새로운 문법으로 넘기면서도 그 문법의 경계와 서버 권한을 분리하지 않은 것**입니다. 제출물에는 공격 문자열만 적지 말고 `입력 → 해석기 또는 파일시스템 → 서버 권한 동작 → 차단 지점`을 한 줄 흐름으로 함께 적으세요.

셸은 명령 문자열에서 인자와 제어 문법을 해석합니다. 고정 프로그램을 호출해야 한다면 실행 파일과 인자를 리스트로 넘겨 각각의 경계를 유지할 수 있습니다. 파일 접근은 경로를 실제 위치로 해석한 뒤 공개 디렉터리 아래에 있는지 검사합니다. 심볼릭 링크가 있으면 입력 이름과 최종 위치가 달라질 수 있습니다.

다음 예제는 공백이 있는 문장을 `printf`에 인자 하나로 전달합니다.

```bash
python - <<'PY'
import subprocess

subprocess.run(["printf", "%s\n", "hello world"], check=True)
PY
```

출력은 `hello world` 한 줄입니다. 다음으로 [경계 예제 코드](../../examples/boundaries.py)의 `read_file`과 `save_text_upload`를 읽으세요. 전자는 `resolve()`로 경로를 해석한 뒤 허용 디렉터리 아래인지 확인합니다. 후자는 `.txt`, 1 KiB 제한, UTF-8 디코딩을 검사하고 서버에서 생성한 파일명으로 저장합니다. 아래 예제는 정상 파일 읽기와 저장 결과의 이름을 확인합니다.

```bash
python - <<'PY'
from pathlib import Path
from tempfile import TemporaryDirectory

from examples.boundaries import read_file, save_text_upload

with TemporaryDirectory() as temporary:
    root = Path(temporary)
    (root / "public").mkdir()
    (root / "public" / "hello.txt").write_text("hello", encoding="utf-8")
    print(read_file(root, "hello.txt", safe=True))
    saved = save_text_upload(root / "uploads", "notes.txt", b"hello")
    print(saved.suffix, saved.name == "notes.txt", saved.read_text(encoding="utf-8"))
PY
```

예상 결과는 `hello`와 `.txt False hello`입니다. `False`는 저장 파일명이 클라이언트가 제공한 이름과 다르다는 뜻입니다.
