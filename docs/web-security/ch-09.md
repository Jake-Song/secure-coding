## SSRF를 왜 배우나

SSRF(Server-Side Request Forgery)는 사용자가 지정한 목적지로 **서버가 대신 요청을 보내게 만드는 문제**입니다. 일반적인 외부 요청의 흐름은 다음과 같습니다.

```text
사용자 브라우저 ──요청──> 웹 서버 ──허용된 외부 API──> 공개 서비스
```

SSRF가 생기면 사용자가 목적지를 바꿀 수 있습니다.

```text
공격자 ──URL 조작──> 웹 서버 ──서버 네트워크 권한──> 내부 서비스·관리 API·메타데이터 서비스
                                      └── 응답 또는 부작용이 공격자에게 전달됨
```

핵심은 URL 문자열 자체가 아니라 **요청을 보내는 주체가 브라우저가 아니라 서버라는 점**입니다. 서버는 브라우저가 접근하지 못하는 사설 네트워크, 로컬호스트, 클라우드 메타데이터 주소에 접근할 수 있고, 내부 서비스가 서버의 IP나 인증 헤더를 신뢰할 수도 있습니다. 따라서 로그인된 사용자라는 이유만으로 임의의 URL을 서버에 전달해서는 안 됩니다.

### 공격이 성립하는 팩터

다음 조건이 겹칠수록 SSRF 위험이 커집니다.

| 공격 팩터 | 확인할 질문 | 문제가 되는 결과 |
|---|---|---|
| 목적지 제어 | URL, 호스트, 포트, 경로 중 사용자가 바꿀 수 있는 값이 있는가? | 내부 서비스로 요청을 돌림 |
| 서버의 네트워크 도달성 | 서버가 사설망·루프백·링크 로컬 주소에 접근할 수 있는가? | 외부 사용자가 직접 접근할 수 없는 대상에 도달함 |
| 응답 또는 부작용 노출 | 서버가 응답 본문을 반환하거나 상태 변경 요청을 허용하는가? | 내부 정보 유출, 내부 API 호출, 포트 탐색 |
| 이름 해석·리다이렉트 | 검사한 호스트와 실제 연결 대상이 끝까지 같은가? | 공개 호스트 검사 후 내부 주소로 변경됨 |
| 서버 권한의 자동 전달 | 내부용 인증 헤더·클라우드 자격 증명을 요청에 붙이는가? | 서버가 가진 권한으로 내부 자원에 접근함 |

예를 들어 `http://internal.lab/config`가 공격자가 직접 접근할 수 없는 내부 설정 서비스라고 합시다. 서버가 이 URL을 받아 요청하고 응답을 사용자에게 돌려주면, 공격자는 내부 서비스의 비밀을 읽는 우회 통로를 얻습니다. 응답을 돌려주지 않더라도 내부 관리 API에 `POST`, `PUT`, `DELETE`를 보낼 수 있다면 정보 변경이나 작업 실행 문제가 될 수 있습니다.

### 방어는 URL 문자열 비교보다 목적지 정책이어야 한다

`url.startswith("https://catalog.lab")` 같은 문자열 검사는 URL의 실제 의미를 검증하지 못합니다. 파싱되지 않은 문자열에는 사용자 정보, 다른 포트, 다른 경로, 인코딩, 리다이렉트가 섞일 수 있습니다. 일반적인 방어 검토 순서는 다음과 같습니다.

1. URL을 파싱하고 허용할 스킴(`https` 등), 호스트, 포트, 경로를 명시합니다.
2. 가능하면 임의 URL 대신 허용 목록의 서비스 ID를 받아 서버가 URL을 선택합니다.
3. 호스트를 해석한 모든 IP 주소를 검사하고 루프백, 사설, 링크 로컬, 예약 주소와 허용하지 않은 IPv6 범위를 차단합니다.
4. 리다이렉트를 사용한다면 최종 목적지를 다시 같은 정책으로 검사합니다. 가장 단순한 정책은 리다이렉트를 끄는 것입니다.
5. DNS 재바인딩처럼 검사 시점과 연결 시점의 주소가 달라지는 경우를 고려하고, 연결 대상 고정과 네트워크 송신 정책을 함께 적용합니다.
6. 연결·응답 크기·리다이렉트 횟수에 제한을 두고, 사용자 쿠키나 내부 인증 헤더를 외부 입력 목적지에 자동 전달하지 않습니다.

애플리케이션 검사는 방화벽이나 서비스 계정의 송신 제한을 대신하지 않습니다. 애플리케이션에서 목적지를 허용 목록으로 제한하고, 네트워크에서도 내부 관리망과 메타데이터 주소로의 불필요한 송신을 차단해야 방어가 한 겹 더 생깁니다.

SSRF는 사용자가 제공한 목적지 정보를 서버가 사용해 요청을 보내는 기능에서 발생할 수 있습니다. 네트워크 접근 권한은 서버가 갖고 있으므로 목적지 정책도 서버가 적용해야 합니다. [경계 예제](../../examples/boundaries.py)의 `fetch_fixture`는 URL 문자열을 키로 미리 정한 응답을 돌려주는 모델입니다.

```bash
python - <<'PY'
from examples.boundaries import PUBLIC_URL, fetch_fixture

print(fetch_fixture(PUBLIC_URL, safe=True))
PY
```

`public catalog`가 출력됩니다. 다음은 이 실습에서 취약한 목적지 선택과 방어된 선택을 나란히 비교하는 코드입니다.

```bash
python - <<'PY'
from examples.boundaries import fetch_fixture

internal_url = "http://internal.lab/config"
print(fetch_fixture(internal_url, safe=False))
try:
    fetch_fixture(internal_url, safe=True)
except PermissionError as error:
    print(type(error).__name__, error)
PY
```

취약한 호출은 `FAKE_INTERNAL_SECRET`를 출력하고, 방어된 호출은 `허용한 목적지가 아닙니다`로 거부됩니다. 여기서 `safe=True`는 공개 URL 하나를 정확히 허용하는 가장 단순한 allowlist입니다. 실제 HTTP 클라이언트에서는 DNS 결과, 리다이렉트 대상, IPv4·IPv6 주소, 연결 시점의 주소, 네트워크 송신 정책까지 추가로 검토해야 합니다. 이 예제는 실제 DNS 조회나 네트워크 요청을 하지 않으므로, 운영 환경의 SSRF 방어가 완성되었다는 증거가 아닙니다.

API에서도 클라이언트가 보낸 필드를 서버가 그대로 반영하면 속성별 인가가 빠질 수 있습니다. 이를 mass assignment라고 부릅니다. [앱 코드](../../app.py)의 `safe_profile`에서 **JSON 객체 → `display_name` 한 필드 → 문자열과 길이 확인 → 현재 사용자 행만 갱신**하는 흐름을 따라가세요. 일반 사용자의 수정 가능 속성은 `display_name`이고, 관리자 여부는 서버가 통제합니다.
