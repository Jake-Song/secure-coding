# AI 서비스 보안 과정

Alice가 “내 회의 메모를 요약해 줘”라고 요청한다. 이때 서버는 Alice가 읽을 수 있는 메모를 고르고, 모델에는 요약에 필요한 내용만 전달한다. 이 과정을 따라가며 **어떤 데이터가 모델에 들어가고, 어떤 결과가 사용자에게 보이며, 모델이 제안한 행동을 누가 승인하는지** 검증한다.

**대상**은 AI 보안 입문자다. **8개 Chapter에 각각 2~3시간**을 잡는다. Python의 리스트·딕셔너리·함수와 웹의 로그인·요청·응답을 조금 알면 된다. 낯설다면 종합 과정 Chapter 3의 Python 연습과 웹 교재의 첫 화면·로그인 관찰부터 시작한다. 본 과정은 합성 메모 두 건과 미리 만든 모의 모델 응답을 사용한다. 첫 실습은 Python 3 표준 라이브러리만으로 실행할 수 있다. [Python 기초 연습](../curriculum.md#1단계-보안과-컴퓨팅-기초) · [웹 앱 구조](../web-security/chapter-02.md)

## 먼저 알아둘 개념

- **학습과 추론** — 학습은 데이터로부터 모델의 가중치를 조정하는 과정이다. 추론은 학습된 모델에 새 입력을 넣고 출력을 얻는 과정이다. 대규모 언어 모델(LLM)에서 **토큰**은 텍스트를 처리하는 단위이고, **문맥**은 해당 요청에서 모델이 참조할 수 있게 제공한 정보다.
- **검색 증강 생성(RAG)** — 서버가 저장소에서 관련 문서를 찾고, 그 내용을 모델의 문맥에 넣어 응답을 생성하는 방식이다. 문서를 검색에 추가해도 가중치는 바뀌지 않는다. **임베딩**은 텍스트를 숫자 벡터로 나타내 비슷한 문서를 찾는 데 쓸 수 있다. 첫 실습은 검색과 권한 검사를 눈으로 확인하기 위해 단어 포함 여부로 문서를 찾는다.
- **도구 호출** — 모델이 기능 이름과 인자를 제안하고, 앱이 허용된 요청인지 확인해 실행하는 구조다. 예를 들어 모델이 `search_notes`를 제안하면 앱이 현재 로그인한 사용자의 권한으로 검색한다.
- **신뢰 경계** — 데이터가 다른 권한이나 운영 주체의 영역으로 넘어가는 지점이다. 메모가 저장소에서 모델로 넘어가는 지점과 모델 출력이 앱 기능으로 전달되는 지점에 각각 필요한 검사를 표시한다.

## Chapter 1 · 데이터 흐름과 보호 대상

**실습.** 종이에 `브라우저 → 앱 → 문서 검색 → 모델 → 앱 → 브라우저`를 그린다. 로그인한 사용자 ID, 원본 메모, 선택된 문서, 생성된 응답이 어느 화살표를 지나는지 적는다. 앱이 외부 모델을 쓰는 경우를 가정하고 어느 화살표에서 다른 운영 주체에게 데이터가 넘어가는지 표시한다. 각 화살표를 그릴 때 기존 메모 앱의 로그인과 메모 조회 흐름을 참고한다. [위협 모델링 기초](../curriculum.md#1단계-보안과-컴퓨팅-기초) · [웹 앱 구조](../web-security/chapter-02.md)

**완료 기준.** 비로그인 사용자의 문서 접근, 타인 문서의 모델 전송, 출처 없는 답변에 대해 각각 어디서 검사할지 흐름도에 표시한다.

## Chapter 2 · 검색 권한과 개인정보 최소화

**기초.** 인증으로 사용자를 확인하고, 인가로 그 사용자가 읽을 수 있는 문서를 정한다. 관련도가 높아도 권한이 없는 문서는 모델에 전달할 수 없다. 전송할 문서에서도 요약에 필요 없는 내부 필드는 빼고, 배포 환경에서는 전송 범위와 보관 정책을 확인한다. [종합 과정 · 인증과 웹 및 API 보안](../curriculum.md#3단계-인증과-웹-및-api-보안)

**실습.** 아래 명령을 실행한다. 호출부의 사용자 이름은 서버가 로그인 세션에서 확인했다고 가정한다. 두 메모에는 같은 검색어 `회의`가 들어 있지만, 검색 후보는 소유자로 먼저 제한한다. 검색 결과는 모델에 전달할 문맥을 나타낸다.

```bash
python3 - <<'PY'
notes = [
    {"id": "A1", "owner": "alice", "text": "회의는 오전 10시"},
    {"id": "B1", "owner": "bob", "text": "회의는 오후 2시"},
]


def build_context(session_user, keyword):
    if session_user is None:
        return []

    owned_notes = [note for note in notes if note["owner"] == session_user]
    return [
        {"id": note["id"], "text": note["text"]}
        for note in owned_notes
        if keyword in note["text"]
    ]


for user in ("alice", "bob", None):
    context = build_context(user, "회의")
    print(user or "비로그인", [note["id"] for note in context])

print("검색 결과 없음", build_context("alice", "식사"))
PY
```

```text
alice ['A1']
bob ['B1']
비로그인 []
검색 결과 없음 []
```

**완료 기준.** 두 사용자의 문맥과 빈 결과를 비교한다. 각 사용자에게 전달되는 문서 ID를 적고, 소유자 이름을 문맥에서 뺀 이유를 설명한다. 기존 앱에서도 소유자 검사가 어떻게 적용되는지 확인한다. Flask 환경이 준비돼 있다면 저장소 루트에서 `python -m unittest tests.test_app.WebLabTests.test_safe_idor_allows_owner_and_blocks_other_user -v`를 실행한다. [기존 앱의 소유권 회귀 테스트](../../tests/test_app.py)

## Chapter 3 · 프롬프트 인젝션과 출력 검증

Jailbreak와 간접 인젝션의 차이, 에이전트 도구 오용과 최근 공개 사례를 먼저 읽는다. [최신 AI 해킹 기법과 방어](ai-hacking-techniques.md)

**기초.** 프롬프트 인젝션은 사용자 입력이나 검색 문서의 텍스트가 모델에서 지시로 처리되어 앱이 의도한 동작을 바꾸는 문제다. 문서의 텍스트는 요약할 데이터로 처리한다. 앱은 모델의 응답을 받으면 형식과 출처를 검사하고, 화면에 표시할 문자열은 텍스트로 렌더링한다. 출처 ID가 허용 목록에 있어도 요약 내용이 그 문서와 일치하는지는 별도로 확인해야 한다. [OWASP LLM 애플리케이션 위험 목록](https://genai.owasp.org/top-10-for-llm-applications-2026/)

**실습.** Alice에게 허용된 문서가 `A1`뿐일 때, 다음 모의 응답을 만들어 앱의 출력 검사를 표나 Python 함수로 적는다. 이 기능은 요약 문자열 `summary`와 문서 ID 목록 `sources`를 담고, 요약을 표시하려면 출처가 한 건 이상 필요하다.

| 모의 응답 | 기대 판정 |
|---|---|
| `summary`는 문자열, `sources`는 `["A1"]` | 표시 허용 |
| `summary`는 문자열, `sources`는 `["B1"]` | 출처 범위 위반으로 표시 보류 |
| `summary`는 문자열, `sources`는 `[]` | 출처가 없어 표시 보류 |
| `summary`가 배열, `sources`가 누락됨 | 형식 오류로 표시 보류 |

**완료 기준.** 검사 규칙에 형식과 출처 범위가 모두 들어 있다. 허용된 출처 `A1`을 달고 틀린 회의 시간을 적은 답변에는 어떤 내용 검증이 추가로 필요한지 설명한다.

## Chapter 4 · 도구 권한과 사람 승인

**기초.** 앱의 최소 권한은 작업에 필요한 권한만 부여하는 원칙이다. 모델이 낸 도구 요청은 앱에 대한 제안이다. 앱은 기능과 인자, 현재 사용자 권한을 검사하고, 상태를 바꾸거나 정보를 공유하는 동작에는 정책에 따라 사람 승인을 요구한다. [네트워크 접근 정책의 기본 거부 예제](../network-security/chapter-07.md) · [OWASP LLM 애플리케이션 위험 목록](https://genai.owasp.org/top-10-for-llm-applications-2026/)

**실습.** `search_notes`, `share_note`, 미등록 기능을 행으로 놓고 허용 조건을 적는다. `search_notes`는 로그인한 사용자에게 자기 문서 검색만 허용한다. `share_note`는 본인 소유 확인과 공유 대상 확인을 거쳐 승인 대기 상태로 보낸다. 공유 요청은 표에서만 판정하고 로컬 실습에서는 승인 상태만 기록한다.

**완료 기준.** 본인 문서 검색은 허용, 타인 문서 공유와 미등록 기능은 거부, 본인 문서 공유는 승인 전까지 대기다. 승인 대상에는 문서 ID와 수신자가 함께 표시된다.

## Chapter 5 · 모델·데이터 공급망

**기초.** AI 서비스는 모델 가중치, 학습 데이터, 검색 문서, 라이브러리와 설정에 의존한다. 학습 데이터 오염은 학습 과정의 입력에 영향을 주는 위험이고, 검색 문서의 무단 변경은 추론에 전달되는 문맥에 영향을 준다. 추론 단계에는 입력 변화에 따른 모델 오류와 출력에서의 개인정보 노출도 따로 점검할 수 있다. [NIST 적대적 기계학습 분류, 2025년판](https://csrc.nist.gov/pubs/ai/100/2/e2025/final)

**실습.** 연습용 모델 버전 `v1`과 합성 문서 묶음 `docs-v1`의 출처, 버전, 변경 승인자, 검증 근거를 표로 적는다. 표에 체크섬을 넣는다면 신뢰할 수 있는 기준값의 보관 위치도 지정한다. 문서 삭제 요청이 들어오면 원본, 검색 색인, 캐시, 로그에 각각 무엇이 남는지 추적한다. [종합 과정 · 공급망](../curriculum.md#5단계-인프라와-소프트웨어-공급망) · [종합 과정 · 데이터 보호](../curriculum.md#6단계-데이터-보호와-위험-관리)

**완료 기준.** 새로운 모델 버전의 출처를 확인할 자료와, 삭제 문서가 검색 결과에서 빠졌는지 검증할 방법을 한 가지씩 적는다.

## Chapter 6 · 보안 평가와 회귀 테스트

**실습.** 정상 검색, 비로그인, 다른 소유자의 문서 제외, 빈 검색 결과, 잘못된 출력 형식, 범위 밖 출처, 승인 없는 공유를 각각 평가 사례로 만든다. 각 행에 입력 조건, 기대 판정, 실제 판정, 근거를 적는다. 검색·권한·출력 검사에서 어느 코드 또는 모의 응답을 평가했는지도 기록한다. 정상 검색이 실제로 성공하는지 확인해 모든 요청을 거부하는 구현도 발견할 수 있게 한다.

**완료 기준.** 정상 사례와 거부·보류 사례가 모두 있다. `통과 사례 수 / 전체 사례 수`와 실패 이유를 적는다. 모의 모델은 앱의 정책과 검사를 반복 검증하는 데 사용한다. 실제 요약의 품질과 출력 변동성은 별도 평가 항목으로 남긴다.

## Chapter 7 · 로그, 탐지와 사고 대응

**실습.** 기존 합성 로그 예제에서 어떤 이벤트들이 경보의 근거가 됐는지 찾는다. 이어 메모 도우미에 `request_id`, 사용자 식별자, 단계, 정책 결과, 모델 버전, 처리 시간을 기록한다고 가정한다. “출처가 허용 범위 밖이라 답변 표시가 보류됐다”는 경보 한 건을 골라 요청에서 응답까지 사건을 정리한다. 로그에는 메모 본문, 원본 프롬프트, 인증 토큰을 넣지 않는다. [기존 로그와 탐지 실습](../network-security/chapter-10.md)

**완료 기준.** 어떤 정책이 무엇을 보류했는지 기록하고, 실제 노출 여부를 확인할 추가 증거를 지정한다. 기능을 잠시 끌 책임자와 재개 전 다시 실행할 평가 항목을 적는다.

## Chapter 8 · 종합 프로젝트와 NIST AI RMF

**과제.** Alice와 Bob의 메모를 다루는 로컬 요약 도우미를 설계한다. 두 사람의 검색 문맥이 소유자별로 분리되는지, 모의 모델 응답에 허용 범위 밖 출처가 있으면 표시가 보류되는지 코드나 테스트로 확인한다. Chapter 1 흐름도, Chapter 4 권한표, Chapter 6 평가 결과, Chapter 7 대응 기록을 함께 제출한다. [기존 보고서 양식](../report-template.md)

NIST는 AI 위험 관리 프레임워크(AI RMF 1.0)의 네 기능으로 책임, 사용 맥락, 검증 근거, 대응 결정을 다룬다. 생성형 AI 프로필은 생성형 AI에 특화된 위험과 대응 조치를 이 틀에 연결한다. 프로젝트에서는 앞에서 만든 결과물을 다음과 같이 연결한다. [NIST AI RMF 1.0](https://doi.org/10.6028/NIST.AI.100-1) · [NIST 생성형 AI 프로필](https://doi.org/10.6028/NIST.AI.600-1)

| AI RMF 기능 | 프로젝트에서 확인할 근거 |
|---|---|
| Govern · 책임과 정책 | 데이터 책임자, 공유 승인자, 사고 대응 담당자가 정해져 있다. |
| Map · 맥락과 위험 파악 | 흐름도에 두 사용자의 문서, 모델로 전달되는 데이터, 신뢰 경계가 표시돼 있다. |
| Measure · 검증 | 정상 요약 경로와 문서 접근 거부 경로의 기대·실제 결과가 기록돼 있다. |
| Manage · 대응과 개선 | 실패했을 때 기능을 제한할 조건, 재검증 방법, 남은 위험의 담당자가 명시돼 있다. |

**완료 기준.** 다른 사람이 실행 명령을 따라 동일한 문서 접근 결과를 확인할 수 있다. 모의 모델에서 확인한 범위와 실제 모델을 도입할 때 추가로 평가할 항목을 설명한다.
